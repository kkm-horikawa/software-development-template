# 長く生きる要求

ここには、複数の変更をまたいで守る背景、利用場面、要求、受け入れ条件を置きます。番号は一度使ったら別の意味へ使い回しません。実装の経緯はIssueとPull Requestへ、一回の設計は増分へ置きます。

この最初の要求は、テンプレート自身が動く例です。新しい製品では内容を製品の要求へ置き換え、同じつなぎ方を保ってください。

## PB-001: 新しい開発で判断の土台を作り直している

要求、設計、コードの読み順、確認方法が案件ごとに散り、同じ開発方針を安全に再利用できない。

### SC-001: 開発者が最初の変更を始める [PB-001]

開発者は、テンプレートから作ったリポジトリで要求を書き、入口から読めるコードと確認を一つの変更として届ける。

#### REQ-001: 開発の約束と動く例を一緒に提供する [SC-001]

システムは、要求からPull Requestまでの進め方、設計と実装の原則、FastAPIとSQLAlchemyで入口から段を読める主例、同じ読み順をGoで示す比較例、自動検査を同じリポジトリで提供する。

##### AC-001: 一つの命令でテンプレート全体を検査できる [REQ-001]

開発者が `just check` を実行すると、文書、要求からテストまでの参照、機密らしい文字列、Pythonの静的検査、FastAPI実例、Go実例、トップダウン構造がすべて検査され、成功時は終了状態0になる。

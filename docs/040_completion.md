# 完了の判断

変更は、コードを書き終えたときではなく、Issueで約束した体験が実際に得られたと確認できたときに完了します。

## 完了に必要なこと

- Issueの困りごと、期待する体験、入口、完了条件が現在の要求になっている。
- 体験を変えた場合、要求のシナリオ、要求、受入基準が製品の現在の姿になっている。
- 増分に、外の振る舞いとテスト、設計上の境界とテストが対応している。
- 全体構造、シーケンス、データ構造へ影響する場合、システムの現在像が同じ変更で更新されている。
- コードが設計原則と実装構造に従っている。
- 自動検査が正常終了している。
- 中心の利用の流れを本物の入口から通し、結果を観測している。
- Pull Requestが、実現した変化、観測結果、変えなかったこと、未確認のことを伝えている。

満たしていない要求は未達、試していない結果は未確認です。実装中に難しいと分かったものを、合意なく「今回は対象外」へ移して完了を作りません。

録画できる入口がある変更は、変更前と変更後を同じ操作で記録します。新しい入口で変更前が存在しない場合は、その事実を書き、変更後だけを録画します。文書や内部整理など録画できない変更は、録画しない理由をPull Requestへ一行残します。

# 開発の進め方

この文書は、要求を受け取ってから変更を届けるまでの正典です。Issue、設計文書、テスト、Pull Requestへ同じ説明を写さず、それぞれの役割で引き継ぎます。

複数の変更をまたいで生きる背景、利用者、目的ごとのシナリオ、シナリオごとの受入条件と具体例、要求、横断的な受入条件は[要求の正典](110_requirements/README.md)へ置きます。システム全体の構造、シナリオを実現するシーケンス、データ構造は[システムの現在像](150_system/README.md)へ置きます。一回の変更を扱うIssueと増分から、その現在像を参照します。

## 一回の変更を通す

```text
困りごと
  ↓ 要求: 課題 → 目的ごとのシナリオ → 要求 → 受入条件と具体例
  ↓ Issue: 今回変える体験と完了条件
増分: Issue番号の中で設計とテストを対応させる
  ↓ 外の振る舞い ↔ 外から確かめるテスト
  ↓ 設計上の境界 ↔ 境界を確かめるテスト
実装
  ↑ 単体 → 結合 → システム → 実際の利用
現在像: シナリオ・受入例とシステムの構造・シーケンス・データを更新
Pull Request: 観測した結果
```

### Issueは期待する体験を書く

誰が、どの入口で、何をして、何が起きれば困りごとが解消するかを書く。CLIならコマンドと出力、GUIなら操作と画面、APIなら要求と応答を具体的にする。作る部品の一覧から始めない。

### 増分で設計とテストを対にする

[増分の雛形](210_increments/_template.md)を一回の変更につき一枚使う。Issue #42なら `INC-42.md` とし、一つのIssueを複数へ分けるときだけ `INC-42-1.md` のように枝番号を付ける。Issue番号が決まってから作るため、増分やテストの番号をIssue作成時に予約しない。

`INC-42.md` の中では `SPEC-42-01`、`ST-42-01`、`AD-42-01`、`IT-42-01` のように番号を付ける。これは一回の変更を設計する住所であり、実行テストの永久名にはしない。実行テストは `SC-001` と `EX-SC001-01` のような現在の受入例で名付け、ST・ITから `テストファイル::テスト名` で結ぶ。別のIssueとは番号が衝突せず、後続の増分で同じ受入テストを更新しても元Issueの名前が残らない。

実装の細部を決める前に、最も大事な利用の流れを一つ通す。層ごとに部品を横へ作り揃えず、入口から保存や外部連携まで、実際に価値が返る縦の一本を先に作る。

その一本は、独立して配備する処理なら `backend/<サービス>`、独立して配布する利用先なら `client/<製品>` の中へ閉じる。単位をまたぐときは相手の内部コードを共有せず、`contracts` に置いた公開契約を通す。各単位が自分の依存関係、起動方法、検査を持つことで、必要になったものだけを後から分離できる。

### 要求とシステムの現在像を更新する

シナリオは、一人の利用者が一つの目的を達成する旅ごとに `110_requirements/シナリオ` へ一ディレクトリで置く。`README.md` は利用目的、`受入例.md` は規則と具体的な前提・入力・操作・観測結果を持つ。増分で体験を追加、変更、削除するときは、同じPull Requestでシナリオ、受入例、要求、横断的な受入条件を現在の姿へ更新する。

受入例は、利用者または外部システムが観測できる結果で判定する。データベース行や内部メソッドを直接見る確認は結合テストへ分ける。人が読むデータの意味は `受入例.md`、Python、Go、ブラウザ操作などが実行する値は使うテストのそばに置き、各テストが準備と後始末を持つ。

その体験を実現する動かす単位と依存は `150_system/全体構造.md`、複数の責任をまたぐ処理順は `150_system/シーケンス`、保存する実体と関係は `150_system/データの構造.md` へ置く。シーケンスは増分ではなくシナリオを参照し、後続の増分で処理順が変われば同じファイルを書き換える。

### 戻しにくい判断だけを決定記録へ置く

公開API、データ形式、データ移行、外部との契約など、後から戻す費用が高い判断は[決定記録の雛形](decisions/_template.md)へ置く。小さな内部実装や作業の経緯は置かない。

### Pull Requestは観測した結果を書く

Issueで約束した中心の流れを実際に通し、入力、出力、画面、保存された状態を記録する。期待した結果を未来形で写さない。試していなければ未確認と書く。

## 不足を見つけたときの戻り先

- 期待する体験が違うならIssueへ戻る。
- 製品全体の目的や受入条件が違うなら要求のシナリオ、受入例、要求、横断的な受入条件へ戻る。
- 外の振る舞いや設計上の境界が足りないなら増分へ戻る。
- 実装だけが違うならコードとテストを直す。
- 全体の動かし方、処理順、データの意味が違うならシステムの現在像へ戻る。
- 長く効く判断が変わるなら決定記録を現在の判断へ更新する。

文書は現在の正解だけを持つ。調査の往復や古い判断はIssue、Pull Request、Gitの履歴へ任せる。

`just check-trace` は、背景からシナリオ、要求、受入条件、具体例、Issue番号を含む外の振る舞い、設計上の境界、`テストファイル::テスト名` で示した実在するテストまで参照が切れていないかを検算します。増分のファイル名、対応Issue、検査設計番号の範囲も確かめます。番号がつながるだけでは意味が正しいと証明できないため、内容はレビューでも確かめます。

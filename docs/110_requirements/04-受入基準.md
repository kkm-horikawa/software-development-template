# 受入基準

> 作業記録アプリのサンプルです。新しい製品では、最初のIssueへ着手する前に本文を削除し、実際のシナリオで要求を満たしたと判定できる状態を書き直してください。

## AC-001: HTTPから作業を始めて結果を確認できる [REQ-001] [SC-001]

HTTPから作業を始める場合は次を満たす。

| 作業名 | 開始時刻 | 応答 | 保存された状態 |
|---|---|---|---|
| ` 設計を書く ` | 省略 | 201、識別子、`設計を書く`、システムが決めた開始時刻 | 整えた作業名と応答と同じ開始時刻を持つ作業が一件 |
| 空白だけ | 省略 | 422と理由 | 何も増えない |

## AC-002: Go CLIから作業を始めて結果を確認できる [REQ-001] [SC-001]

Go CLIから作業を始める場合は次を満たす。

| 入力または状態 | 表示と終了 | 保存された状態 |
|---|---|---|
| `worklog start "設計を書く"` | `開始: 設計を書く`、正常終了 | HTTPと同じ作業が一件 |
| 作業名が空白だけ | 空にできない理由、失敗終了 | 何も増えず、バックエンドを呼ばない |
| 要求を送る前にバックエンドへ到達できない | 開始できなかった理由、失敗終了 | 何も増えない |
| 要求を送った後に応答を受け取れない | 結果を確認できない理由、失敗終了 | 保存の有無は不明。未保存と決めつけて自動再試行しない |

開始時刻の明示指定は現在の対応入口にありません。追加する増分では、正常値、省略、解釈できない値、許されない未来時刻をこの判断表へ足し、各入口で同じ意味になることを確かめます。

# シナリオ

現在提供できる体験を、利用者が一つの目的を達成する旅ごとに置きます。

- [SC-001 作業を始める](SC-001-作業を始める.md)

## 分け方

HTTP、CLI、GUIは入口であり、それだけでは別シナリオにしません。目的、きっかけ、成功時保証が同じなら、一つのシナリオに共通の主成功シナリオを書き、入口別経路の表へ違いを置きます。システム内部の呼び先が違う場合は、`150_system/シーケンス` の同じSCファイルで入口ごとに図を分けます。

目的、利用者の判断、完了後に残る状態のどれかが変わる場合は、別シナリオにします。たとえば「いま作業を始める」と「終わった作業をあとから実績として追加する」は、同じ作業名と時刻を扱っても、きっかけと成功時保証が違うため別です。

## 記載の厚さ

[_template.md](_template.md)は、一般的なユースケース記述のデフォルト形式、完全形式、RUP形式から、現在像を保つために効く項目をまとめています。

概要、主アクター、事前条件、きっかけ、最低保証、成功時保証、主成功シナリオ、拡張は常に書きます。入口または入力が複数ある場合は対応表も書きます。利害関係者と利益、特別な要件、技術・データのバリエーション、サブユースケースと拡張点は、複雑さや失敗時の影響が正当化する場合だけ詳しくし、無ければ「なし」とします。

スコープは責任を持つ製品またはシステム、レベルは原則「利用者の目的」です。内部処理の一段をSCとして量産しません。複数のシナリオで本当に再利用する利用目的だけをサブユースケースとして切り出します。

## 入力とエッジケース

必須か任意か、省略時にシステムが何を決めるかは、シナリオの入力表へ置きます。主成功シナリオと違う条件は、対応する段番号へ結び付けて拡張へ置きます。同じ成功時保証へ戻る経路と、目的へ到達できず最低保証を守って終了する経路を、戻り先または終了まで書き分けます。

開始時刻を任意で受ける場合は、同じ「作業を始める」シナリオの入力表へ次のように足します。

| 入力 | 必須 | 省略した場合 | 受け付ける値 |
|---|---|---|---|
| 開始時刻 | 任意 | システムが現在時刻を使う | 利用者の地域で解釈でき、製品が定めた範囲の時刻 |

有効な時刻を指定した経路は主成功シナリオの時刻決定段に結ぶ拡張へ、解釈できない時刻や製品の規則で許されない時刻は最低保証を守って終了する拡張へ置きます。具体的な境界値と入口ごとの応答は受入基準の判断表へ置き、シナリオへ全入力を列挙しません。

使わない項目は「なし」と短く書き、見出し自体は残して、書き忘れと対象外を区別します。

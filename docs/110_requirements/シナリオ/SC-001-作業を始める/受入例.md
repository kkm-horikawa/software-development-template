# 作業を始める受入条件と具体例

対応する利用目的: [SC-001 作業を始める](README.md)

受入条件は「何を達成するか」、具体例は「どの前提、入力、操作、観測結果で判定するか」を受け持ちます。具体例は一つあれば、受入条件の全範囲を表したことにはなりません。

## AC-SC001-01: 対応する入口から開始結果を確認できる [REQ-001] [SC-001]

どの対応入口を使っても、利用者は同じ意味の作業を開始できたことを、入口から返る結果で判断できる。

### EX-SC001-01: HTTPで前後に空白のある作業名を始める [AC-SC001-01]

- 前提: 識別子と時刻を固定した、作業を受け付けられるシステム
- 入力: `POST /activities` へ `{"title":" 設計を書く "}`
- 観測: 応答状態201と、固定した識別子、`設計を書く`、固定した開始時刻
- 方法: 自動
- 実行物: `backend/worklog-api/tests/acceptance/sc_001/test_http_start_activity.py::test_http_start_activity`

### EX-SC001-02: Go CLIで作業を始める [AC-SC001-01]

- 前提: 使い捨ての保存先で動くバックエンド
- 入力: `worklog start "設計を書く"`
- 観測: 標準出力が `開始: 設計を書く`、標準エラーが空、終了状態0
- 方法: 自動
- 実行物: `tests/acceptance/sc_001/test_cli_start_activity.py::test_cli_start_activity`

## AC-SC001-02: 受け付けない入力を開始したように扱わない [REQ-001] [SC-001]

作業名が空なら、どの入口でも理由を返し、開始したと表示しない。

### EX-SC001-03: HTTPで空の作業名を拒む [AC-SC001-02]

- 前提: 作業を受け付けられるシステム
- 入力: `POST /activities` へ `{"title":"   "}`
- 観測: 応答状態422と、作業名を空にできない理由
- 方法: 自動
- 実行物: `backend/worklog-api/tests/acceptance/sc_001/test_http_start_activity.py::test_http_start_activity`

### EX-SC001-04: Go CLIで空の作業名を拒む [AC-SC001-02]

- 前提: CLIを実行できる状態
- 入力: `worklog start "   "`
- 観測: 標準エラーに作業名を空にできない理由、標準出力は空、失敗終了
- 方法: 自動
- 実行物: `tests/acceptance/sc_001/test_cli_start_activity.py::test_cli_start_activity`

## AC-SC001-03: 接続できない作業を開始したように扱わない [REQ-001] [SC-001]

要求を送る前にバックエンドへ接続できなければ、CLIは開始結果を表示せず失敗する。

### EX-SC001-05: Go CLIが到達不能なバックエンドを報告する [AC-SC001-03]

- 前提: 指定した接続先でバックエンドが動いていない
- 入力: 到達不能な接続先で `worklog start "設計を書く"`
- 観測: 標準出力は空、標準エラーに開始を依頼できない理由、失敗終了
- 方法: 自動
- 実行物: `tests/acceptance/sc_001/test_cli_start_activity.py::test_cli_start_activity`

## テストデータ

| 名前 | 意味 | 値 | 実行時の置き場所 |
|---|---|---|---|
| 通常の作業名 | 前後の空白を除いて開始できる | ` 設計を書く ` | HTTP受入テストの `task.csv` |
| 空の作業名 | 前後の空白を除くと無効 | 空白三文字 | HTTPとGo CLIそれぞれの `task.csv` |
| 固定した開始結果 | 出力を毎回同じにして意味を比較する | UUID `1111...`、`2026-09-09T10:00:00Z` | 各テストのfixture |
| 到達不能な接続先 | 要求送信前の接続失敗 | OSが割り当てた未使用ポート | CLI受入テストのfixture |

人が読む値と期待結果はこの文書を正とします。Python、Go、ブラウザ操作などが実行する形は、使うテストのそばへfixture、factory、表駆動データとして置きます。別テストが残した状態には依存せず、各テストが準備と後始末を受け持ちます。

## 手動確認

現在の具体例はすべて自動化できます。見た目、操作感、端末固有など自動化しない具体例が増えた場合は、`tests/acceptance/manual` にSC番号を持つ確認書を置き、前提、準備、操作、観測、証跡、後始末を固定します。

## 現在まだ受け入れないこと

- 開始時刻の明示指定
- 作業の一覧、終了、修正、認証
- 要求送信後に応答だけ失われた場合の結果照会と、重複しない再試行

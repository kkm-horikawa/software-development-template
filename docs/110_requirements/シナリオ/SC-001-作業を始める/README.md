# SC-001: 作業を始める [PB-001] [PB-002]

## 文脈

| 項目 | 内容 |
|---|---|
| スコープ | 作業記録システム |
| レベル | 利用者の目的 |

## 概要

作業を記録する人が、利用中の入口から着手した作業を伝え、同じ意味の一件として残ったことを確認する。

## アクター

- 主アクター: 作業を記録する人
- 関係する立場と利益: 新しい入口を提供する開発者は既存入口と同じ意味を保ちたい。保守する開発者は失敗時に一部だけ保存される状態を防ぎたい

## 事前条件

- 作業を記録する人が、HTTPまたはGo CLIのどちらかを利用できる。
- バックエンドが作業を保存できる状態で動いている。

## きっかけ

作業を記録する人が、新しい作業へ着手する。

## 入力

| 入力 | 必須 | 省略した場合 | 現在受け付ける値 |
|---|---|---|---|
| 作業名 | 必須 | 受け付けない | 前後の空白を除いて空でない文字列 |
| 開始時刻 | 入力不可 | システムが現在時刻を決める | このサンプルでは明示指定をまだ受け付けない |

## 入口別経路

| 入口 | 利用者の入力 | 成功時に見える結果 |
|---|---|---|
| HTTP | `POST /activities` に作業名を送る | 応答状態201と、識別子、整えた作業名、開始時刻 |
| Go CLI | `worklog start <作業名>` を打つ | `開始: <作業名>` |

入口が増えても、目的と成功時保証が同じならこの表へ足す。入口によってシステム内部の呼び先が変わる場合は、同じSC-001のシーケンスへ入口別の図を足す。

## 最低保証

- 無効な入力と保存失敗では、作業を一部だけ残さない。
- 保存できていない作業を、開始したとは返さない。
- 通信が途中で切れて結果を確認できない場合は、成功とも未保存とも決めつけず、結果不明として扱う。

## 成功時保証

- 空でない作業名、識別子、開始時刻を持つ作業が一件保存されている。
- 利用者が、どの入口でも作業を開始できたと判断できる結果を受け取っている。

## 主成功シナリオ

1. 作業を記録する人が、利用中の入口へ作業名を渡す。
2. システムが作業名を整え、有効か確かめる。
3. システムが識別子と開始時刻を決める。
4. システムが作業を一件保存する。
5. システムが、その入口に合う形で開始結果を返す。
6. 作業を記録する人は、記録が残ったと判断して作業を続ける。

## 拡張

- 2a. 作業名の前後に空白がある場合、システムは空白を除いた名前で3へ進む。
- 2b. 作業名が空の場合、理由を返し、何も保存せず終了する。
- 4a. 保存に失敗した場合、開始できなかった理由を返し、成功を表示せず終了する。
- 1a. CLIがバックエンドへ接続できない場合、CLIは開始できなかった理由を返し、成功を表示せず終了する。
- 5a. 要求を送った後に応答を受け取れない場合、CLIは結果を確認できないと返す。作業が保存された可能性があるため、未保存と決めつけて自動再試行しない。

開始時刻を任意指定できる増分では、入力表へ「省略時は現在時刻」を書き、指定された正常値を3a、解釈できない値を3bのように足す。あとから終わった作業を登録するなど、きっかけと成功時保証が変わるなら別シナリオにする。

## 特別な要件

なし。

## 技術・データのバリエーション

- HTTPはJSONで作業名を受け、JSONで開始した作業を返す。
- Go CLIは命令の引数で作業名を受け、人が読める一行で結果を返す。

## 備考

作業の一覧、終了、修正、認証はこのサンプルでは提供しない。

要求が届いた後の通信断による結果不明と、再試行時の二重登録を解消する識別子や照会の仕組みも未対応。

# テストの考え方

テストはコードの行を通った数ではなく、利用者が渡す入力と、返る結果、起きる状態変化を守るために作ります。

## 利用者に近い順で考える

受入テストとシステムテストで、中心の利用の流れを外から確かめます。結合テストで、採用した境界が実際につながることを確かめます。単体テストで、小さな規則、境界値、失敗条件を速く確かめます。

単体テストが多くても、利用者の流れを確かめたことにはなりません。Issueの場面から正常系、境界値、失敗時の入力を導きます。

## シナリオから受入例を作る

長く生きる利用目的のSC一件を、受入テスト一件と同一視しません。SCの最低保証、成功時保証、主成功シナリオ、拡張から受入条件を取り出し、正常、代替、例外、境界値の具体例を作ります。一つの具体例だけで受入条件の全範囲を表したとは考えません。

受入条件は「何を達成するか」、具体例は「どの前提、入力、操作、観測結果で判定するか」を受け持ちます。具体例ごとに自動または手動を選び、実行物を示します。

## 実装の写しにしない

外からのテストは、公開入口へ何を渡し、利用者または外部システムへ何が返り、何が起きるかだけを見ます。データベース行、内部メソッドの呼び出し順や内部の値を覗くテストは、受入テストから外して結合または構造検査へ分けます。

構造そのものを守る必要がある場合は、振る舞いのテストとは別に静的な構造検査を置きます。FastAPIとGoの例では、それぞれの言語の構文木を読む検査が、入口から段で読む規則を受け持ちます。

## 外部との境界

モック（実物の代わりになる偽物）は、外部API、データベース、時刻などの入出力境界だけに使います。自分のコード同士をモックで切り離しません。

実物から採った固定データを使う場合は、実物の契約が今も一致するか確かめる契約テストを別に用意します。固定データだけでは、外部が変わってもテストが緑のままになります。

## テストの説明

各テストは、入力と期待する結果を読み取れる名前と構造にします。番号や「実行可能」という宣言だけで済ませません。同じ判断の値違いはまとめ、別の失敗条件は分けます。

増分で設計するシステムテストと結合テストの識別子は、Issue番号の中で付けます。`INC-42.md` の最初のシステムテストは `ST-42-01`、結合テストは `IT-42-01` です。

コード上の実行テストは `test_sc001_ex01_...` のように現在のSCと具体例で名付けます。増分側から `テストファイル::テスト名` で参照し、元Issueの番号を実行テストへ永久に残しません。別Issueの番号は予約せず、増分内の番号だけを `01` から割り当てます。

## テストデータと環境

人が読む値と期待結果はSCの `受入例.md` を正とします。実行形式のデータは、使うテストのそばへfixture、factory、表駆動データとして置きます。画像や外部応答など大きな固定物だけを、対象テスト配下の `fixtures` に置きます。

各テストは自分に必要なデータと保存先を準備し、後始末します。別テストの実行結果、実行順、共有された変更可能な一件へ依存しません。並行実行ではテストまたは実行単位ごとに識別子、利用者、保存先を分けます。

HTTPの作業開始例では、`tests/acceptance/sc_001/task.csv` にケース名、入力、期待する応答を表として置きます。`HTTPStartCases` が列と値を検査して型の付いたリストへ読み込み、`TestHTTPStartActivity` が一行ずつ独立したテストとして実行します。ケース名には受入例の番号を使うため、失敗した行を特定できます。DBの準備と後始末は各行に対して実行します。

CSVの列追加・不足・重複・順序違い、行の列数不一致、不正な応答状態、空の表、重複したケース名は読み込み時に失敗します。入力の空白はテスト対象なので削除しません。新しいAPI項目を追加した場合、CSVへ列を足すだけで自動対応したとは扱わず、読み込みの型、要求の組み立て、期待結果、具体例を一緒に更新します。任意項目が増えても既存の呼び方が有効なら、既存テストは成功したままで構いません。新しい振る舞いの網羅はシナリオから追加します。

平たい値はCSVが適しています。入れ子の要求や応答はJSONなど読みやすい形式を選びます。サーバーや保存先の準備処理まで表へ押し込む必要はありません。

Go CLIの例も、リポジトリ直下の `tests/acceptance/sc_001/task.csv` に正常・空入力・接続不能を置き、`TestCLIStartActivity` が一行ずつ実行します。接続先の状態は `running` または `unreachable`、成功判定は `true` または `false` です。標準出力の列は改行を除いた一行で、空欄なら出力なしを期待します。標準エラーは理由を含むことを確認し、空欄なら標準エラー全体が空であることを確認します。実HTTPサーバーと保存先の準備・後始末は `fixtures.py` が受け持ちます。

テストは同じ目的と準備を持つまとまりごとにクラスで書きます。表の各行は独立したテストとして実行し、可変な状態をクラス変数やテスト間で共有しません。

安定して繰り返す中心系列、境界値、過去に壊れた例は自動化します。見た目、操作感、実機固有、外部環境、未知の失敗探索は手動でよいですが、目的、入口、環境、準備、操作、観測、証跡、後始末を持つ確認書にします。

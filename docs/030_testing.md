# テストの考え方

テストはコードの行を通った数ではなく、利用者が渡す入力と、返る結果、起きる状態変化を守るために作ります。

## 利用者に近い順で考える

受け入れテストとシステムテストで、中心の利用の流れを外から確かめます。結合テストで、採用した境界が実際につながることを確かめます。単体テストで、小さな規則、境界値、失敗条件を速く確かめます。

単体テストが多くても、利用者の流れを確かめたことにはなりません。Issueの場面から正常系、境界値、失敗時の入力を導きます。

## 実装の写しにしない

外からのテストは、公開入口へ何を渡し、何が返り、何が起きるかだけを見ます。内部メソッドの呼び出し順や内部の値を覗くテストは、整理するだけで壊れるため避けます。

構造そのものを守る必要がある場合は、振る舞いのテストとは別に静的な構造検査を置きます。FastAPIとGoの例では、それぞれの言語の構文木を読む検査が、入口から段で読む規則を受け持ちます。

## 外部との境界

モック（実物の代わりになる偽物）は、外部API、データベース、時刻などの入出力境界だけに使います。自分のコード同士をモックで切り離しません。

実物から採った固定データを使う場合は、実物の契約が今も一致するか確かめる契約テストを別に用意します。固定データだけでは、外部が変わってもテストが緑のままになります。

## テストの説明

各テストは、入力と期待する結果を読み取れる名前と構造にします。番号や「実行可能」という宣言だけで済ませません。同じ判断の値違いはまとめ、別の失敗条件は分けます。

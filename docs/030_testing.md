# テストの考え方

利用者の目的から正常・代替・例外・境界値を選び、外から見た結果を確かめます。コードの実装を写したテストや、件数だけの多さで品質を判断しません。

## ケースと実行方法

Pythonは同じ目的をクラスへまとめ、CSVの各行を独立したテストとして実行します。GoはTest関数とサブテストを使います。受入例の文書にはケースの名前と実行先だけを置き、値や期待結果を写しません。

例の実行先は `ファイル.py::クラス::メソッド[EX-SC001-01]` の形です。`uv run --project backend/worklog-api pytest '<実行先>'` で一件を再現できます。参照検査はpytestが実際に収集したケースと照合し、コメントに名前があるだけでは合格しません。

## 入力と期待結果の正本

平たいデータはCSV、入れ子はJSON等、手動なら確認書に置きます。シナリオには一般の規則、データには具体値を持たせます。任意項目を追加しても既存入力が有効なら既存テストは成功して構いません。新しい振る舞いの網羅はシナリオから考えます。

CSV読み込みは列の不足・追加、行の不整合、不正値、空の表、重複したケース名を拒みます。入力の空白は検査対象なので保持します。読み込み器自身のテストには独立した小さなCSVを使い、実ケースの追加や並べ替えを妨げません。

サンプルのCSVは次にあります。

- [HTTP](../backend/worklog-api/tests/acceptance/sc_001/task.csv): 作業名、応答状態、返る作業または理由
- [CLI](../tests/acceptance/sc_001/task.csv): 接続先状態、作業名、標準出力一行、標準エラーに含む理由、成功判定

CLIの標準出力は空欄なら出力なし、値があればその一行と改行です。標準エラーは空欄なら全体が空であることを確認します。接続先状態は[読み込みの型](../tests/acceptance/sc_001/cases.py)で定めます。

## 環境と観測

各ケースが保存先やサーバーを準備・解放します。別ケースの結果や実行順に依存しません。モックは外部API・DB・時刻等の入出力境界に限り、自分のコード同士を切り離しません。

受入テストはHTTP応答、画面、標準出力など外から観測できる結果を見ます。DB行や内部メソッドは結合・構造検査で確かめます。契約テストは生成物同士の一致に加え、実際の要求・応答も公開契約に照らします。

自動化しない例は[手動確認書](../tests/acceptance/manual/README.md)へ、環境、準備、操作、観測、判定、証跡、後始末を書きます。未知の失敗を探す探索的テストは目的と時間枠を持ち、既知の例の合否判定と分けます。

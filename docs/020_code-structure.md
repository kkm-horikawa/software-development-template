# 入口から同じ粒度の段を下りる

公開入口のメソッドを、利用の流れを示す「実行できる目次」にします。そこへ並ぶ呼び出しは同じ細かさに揃え、呼ばれた先で一段だけ詳しくします。

## 基本形

```text
受付.run
  → 入力を読む
  → 利用の手順へ渡す
  → 結果を書く

利用の手順.run
  → 業務の値を作る
  → 業務の状態を変える
  → 保存を依頼する
```

一つのメソッドを数行へ縮めることが目的ではありません。一つの名前で説明できる責任を一つだけ持たせます。兄弟として並ぶ呼び出しへ、利用の段とSQLやJSON変換のような実装詳細を混ぜません。

## 守る規則

- 入口だけを読めば、中心の利用の流れと順番を説明できる。
- 同じメソッドに並ぶ呼び出しは、同じ抽象度に揃える。
- 呼ばれたメソッドは、一段だけ詳しい責任へ降りる。
- 状態と依存は、その流れを受け持つ型の欄へ置く。
- 型とメソッドは業務の言葉で名付ける。
- 入力形式、HTTP、SQL、画面表示は境界へ閉じ込める。
- 内部のエラーは上へ返し、利用者向けの表現への変換は境界で行う。

## 避ける形

次のように進行と詳細が混ざると、全体を知るために細部まで読まなければなりません。

```text
run
  → JSONを直接解析する
  → 業務の条件をその場で分岐する
  → SQLを組み立てる
  → 応答を書く
```

また、名前のない小さな関数をファイルへ並べるだけでは、責任を持つ場所が分かりません。状態と依存を共有する一連の流れは、一つの型へ閉じます。

## DDD、クリーンアーキテクチャとの関係

DDDは「何を概念として置くか」を決めます。クリーンアーキテクチャは「どちらがどちらを知るか」を決めます。この文書の段は「人がどの順番で理解するか」を決めます。

例えば、CLIの入口は入力を読み、利用の手順へ渡し、結果を書きます。利用の手順は業務の型へ命令し、保存の境界へ依頼します。保存の実装はその境界を満たしますが、業務の型はデータベースを知りません。

主となる動く例は [`examples/python/fastapi`](../examples/python/fastapi/README.md) にあります。FastAPIのHTTP入口から利用の手順、ドメイン、SQLAlchemyの保存までを実際につなぎます。同じ読み順を [`examples/go/topdown`](../examples/go/topdown/README.md) のCLIでも見比べられます。構造検査は、それぞれの入口と利用の手順が自分の段のメソッドだけを呼び、低水準の外部処理を直接使っていないことを確かめます。

## レビューするときの問い

入口を読んだだけで「何が、どの順番で起きるか」を言えるか。途中で急に細かな条件や外部技術へ降りていないか。次の詳細へ進むための名前が、業務の言葉になっているか。この三つを最初に確かめます。

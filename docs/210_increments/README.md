# 増分

> `INC-1.md` と `INC-3.md` は作業記録アプリのサンプルです。新しい製品では最初のIssueへ着手する前に削除してください。残したまま製品の増分を足すと、存在しないIssueとテストが正典へ混ざります。

一回の変更につき一枚の文書を置きます。Issueを作成して番号が決まってから、[`_template.md`](_template.md)を写します。

## 番号

一つのIssueを一増分で届ける場合は `INC-<Issue番号>.md` とします。Issue #42なら `INC-42.md` です。一つのIssueを複数の増分へ分ける場合だけ `INC-42-1.md`、`INC-42-2.md` のように枝番号を付けます。

増分内の識別子も、増分の名前を含めます。

```text
INC-42.md
  SPEC-42-01
  ST-42-01
  AD-42-01
  IT-42-01

INC-42-2.md
  SPEC-42-2-01
  ST-42-2-01
```

この形なら、別のIssueが並行しても番号が衝突しません。Issueを作る時点でテスト番号を予約せず、増分を書く時点で `01` から割り当てます。Issueが取りやめになっても、増分の連番に欠番ができたとは考えません。Issue番号が、その変更を始めた要求へ戻る入口だからです。

## 役割

増分には、その一回の変更で選んだ体験、外から見える振る舞いとシステムテスト、設計上の境界と結合テストを置きます。検討の往復と完了後の報告はIssueとPull Requestへ残します。

増分が変える現在像は、同じPull Requestで `110_requirements` のシナリオ・要求・受入基準と、`150_system` の全体構造・シーケンス・データ構造へ反映します。増分だけ読まないと現在の製品が分からない状態を作りません。

取り込まれた増分は「そのIssueで何を変えたか」の記録として残し、後続の増分に合わせて現在の姿へ書き換えません。現在の製品を読む入口は `110_requirements` と `150_system` であり、増分を最初から読み直す必要はありません。
